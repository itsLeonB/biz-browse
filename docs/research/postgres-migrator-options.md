# PostgreSQL migrator options

Research checked 2026-11-17. No packages were installed, secrets read, or databases contacted. Nothing has deployed, and existing databases can be reset. This research does not reset them. The existing SQL may be rewritten or squashed, provided the resulting intended schema is preserved.

These tools are **migration runners**, not ORM replacements. The application can keep Postgres.js and its SQL queries.

## Recommendation

**Choose `node-pg-migrate` for review.** It fits the Node stack, tracks migrations, takes a PostgreSQL advisory lock by default, and supports transactional migrations. Its SQL support avoids an ORM or schema rewrite. Pin and test the exact version before adoption. Choose dbmate if a separate SQL-focused CLI is preferable; it needs its migration lock explicitly enabled. Choose Graphile Migrate if migration-file integrity checks justify its stricter development workflow.

**Postgres.js does not have `sql.migrate`.** Its documentation says migrations are outside its scope and lists separate tools. A custom runner around `sql.file` would also need history, locking, ordering and recovery. [Postgres.js migration tools](https://github.com/porsager/postgres#migration-tools).

## Options

| Rank | Runner | Safety and maintenance |
| --- | --- | --- |
| 1 | [node-pg-migrate](https://salsita.github.io/node-pg-migrate/) | Node CLI/API using `pg`, separately from the app's Postgres.js client. Tracks migration names and checks order. Uses a session advisory lock by default and normally wraps migrations in transactions; options include `noLock` and `singleTransaction`. Its SQL loader supports paired `.up.sql` / `.down.sql` files; the legacy loader uses SQL section markers. Current history is not a checksum-based file integrity check; confirm exact pinned-version behavior. No separate binary is required, but the project gains a development dependency and another database driver. [Loaders](https://salsita.github.io/node-pg-migrate/migration-loading-strategies), [API](https://salsita.github.io/node-pg-migrate/api), [runner source](https://github.com/salsita/node-pg-migrate/blob/main/src/runner.ts). |
| 2 | [dbmate](https://github.com/amacneil/dbmate#concepts) | SQL-first standalone CLI, also distributed via npm. Records numeric versions in `schema_migrations` and normally runs each migration in a transaction. **Enable `--migration-lock`** to serialize PostgreSQL migrators; the lock does not protect concurrent database creation. `--strict` rejects out-of-order application and missing applied files. Version-only history has no file checksum; strict mode is not drift detection. Default schema dumping can be disabled. Its SQL files use up/down markers; empty down sections are allowed. The separate binary adds a distribution concern but keeps migration logic independent of app code. [Options and lock](https://github.com/amacneil/dbmate#command-line-options), [format and history](https://github.com/amacneil/dbmate#concepts), [transactions](https://github.com/amacneil/dbmate#migration-options). |
| 3 | [Graphile Migrate](https://github.com/graphile/migrate) | SQL-first, forward-only Node CLI with numbered, hash-linked committed migrations. It checks file integrity and linear history, but hashes do **not** prove the live schema matches the files. Transactions are default; `--! no-transaction` has a single-statement limitation. Its shadow database and repeatable-current-migration workflow add work and can destroy the shadow database. Concurrent-run lock behavior and support for this repo's Node 26 are **unverified**; its README lists older Node LTS versions. [Workflow and integrity](https://github.com/graphile/migrate#editing-a-committed-migration), [transactions](https://github.com/graphile/migrate#disable-transaction). |

A Postgres.js-specific alternative, [postgres-shift](https://github.com/porsager/postgres-shift), uses numbered directories containing `index.sql` or `index.js`. Current maintenance, Postgres.js v4 compatibility, transaction/history atomicity, concurrent locking and checksums were not verified; do not select it on client compatibility alone.

## Clean setup and SQL risks

- [Compose](../../compose.yaml) mounts all six SQL files into PostgreSQL's initialization directory. [Test Compose](../../compose.test.yaml) extends that setup and also loads taxonomy and directory fixtures; the fixtures currently sort after `003` and `004`, respectively. Replace initialization with the chosen runner so a clean database receives migration history as well as schema.
- [`004_price_details.sql`](../../db/004_price_details.sql) explicitly uses `BEGIN`/`COMMIT`, locks `listings`, and refuses to run while any listing is published. PostgreSQL does not nest `BEGIN`; its `COMMIT` ends the outer transaction. A runner's history write can therefore fall outside the schema transaction, leaving applied SQL unrecorded after a failure. When rewriting, let the runner own the transaction; do not merely disable it, which leaves schema and history non-atomic. [PostgreSQL BEGIN](https://www.postgresql.org/docs/current/sql-begin.html), [COMMIT](https://www.postgresql.org/docs/current/sql-commit.html).
- If squashing, preserve the final schema from **all six** files, including columns, defaults, constraints and indexes. The `004` guard and lock protect an upgrade of existing published data; decide their role for a fresh-only initial migration separately rather than silently applying them to later migrations. Compare a clean database built from the rewritten SQL with one built from the six originals, including schema and relevant behavior. No database comparison was run for this note.
- No candidate automatically proves manually changed tables match migration history. Protect applied migration files in review; use schema comparison or separate checks where live drift matters. Test a clean install, a second no-op run, a failed migration and two concurrent runs.

## Where it runs

Use a separate trusted Node/CLI or container step, **not** Worker startup or a request. Run it after the database is ready and before app startup; run test fixtures only after all required migrations. Do not run both the old init scripts and the new runner. Keep production/preview migration credentials out of builds, logs, artifacts and untrusted PR code.

**Superseded:** The former GitHub preview workflow and manual deployment path were removed in #12. Follow the current [Preview instructions](../manual-preview.md): an authorized SWE applies reviewed migrations to the exact isolated Preview database before verification. Never expose production migration credentials to Preview builds. Production deployment controls are tracked separately in #14.

For Neon use a separately supplied **direct, non-pooler** connection for migrations, especially session advisory locks; Neon uses transaction pooling for pooled connections, so session state is not guaranteed across transactions. Confirm project, branch, database and role before writes; keep the app URL and migration URL distinct where needed. [Neon pooling](https://github.com/neondatabase/website/blob/main/content/docs/connect/connection-pooling.md). Actual connection URLs were not inspected.
