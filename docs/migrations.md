# PostgreSQL migrations

## Local and test databases

`npm run migrate` runs the pinned `node-pg-migrate` on the direct `DATABASE_URL`. It reads SQL files in `db/` and records history in `pgmigrations`. The runner owns the transaction and advisory lock. Do not add `BEGIN` or `COMMIT` to migration files. Create future SQL migrations with `npx --no-install node-pg-migrate create NAME --migrations-dir db --migration-file-language sql`.

Compose runs migrations before the app starts. `./scripts/test-compose.sh` creates a separate database, runs the same migrations, loads `tests/taxonomy.sql` and `tests/directory.sql`, and removes that test database. The migration integration test uses its own temporary schema when `TEST_MIGRATION_DATABASE_URL` points to an isolated test database. Never point tests at production.

The initial migration is for an **empty database**. Databases created by the six old SQL files have no runner history. Do not reset them, run the initial migration on them, or mark it as applied without a separate review of their exact schema and data. Back up the database and agree a safe adoption plan first.

## Production: blocked pending provider checks

Do not configure production migration credentials or enable this deployment path until all checks below pass. The actual Cloudflare account's build-secret scope, branch settings and serialization have not been verified. Preview runtime settings do not prove build-secret isolation. Cloudflare documents [build secrets](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/) as available to the build and [branch control](https://developers.cloudflare.com/workers/ci-cd/builds/build-branches/) as controlling production and preview builds. If production build secrets cannot be withheld from other branches, disable all preview builds before adding the secret. Keep the Preview command free of production migrations and credentials. Do not enable the superseded GitHub preview deployment job.

1. Protect the production branch against untrusted pushes. In Worker → Settings → Build → Branch control, select that branch and disable Preview Builds unless provider controls have been verified to exclude production build secrets from every non-production build. Verify actual settings, not only documentation.
2. Confirm one release at a time for the entire database-and-Worker target, including retries, manual releases and other deployment paths. Do not cancel a running migration. Check that an older build cannot deploy after a newer one. Cloudflare lists [one concurrent build on Free and six on paid plans](https://developers.cloudflare.com/workers/ci-cd/builds/limits-and-pricing/); account-wide limits alone do not coordinate external deployments or establish release order. If exclusive, ordered releases cannot be assured, stop; do not configure the production secret.
3. Verify the approved commit is the source of both migration files and the built Worker. Confirm the Cloudflare account, Worker, generated Wrangler configuration and private R2 bucket, and the Neon project, branch, database and migration role. Use a least-privilege, **direct non-pooler** Neon connection; the runner's session lock is not safe through transaction pooling. Never print the URL.
4. Set the build secret `MIGRATION_DATABASE_URL` to that direct connection. Set the public `VITE_CLERK_PUBLISHABLE_KEY` as a build variable. Set runtime `DATABASE_URL`, `CLERK_SECRET_KEY` and `ADMIN_USER_IDS` separately as Worker secrets; do not put the migration credential in Worker runtime settings. A build secret is available to build dependencies and source code, so only trusted builds may receive it.
5. In Worker → Settings → Build, set **Build command** to `npm run build` and **Deploy command** to:

   ```sh
   DATABASE_URL="$MIGRATION_DATABASE_URL" npx --no-install node-pg-migrate up --migrations-dir db --migration-file-language sql && npx --no-install wrangler deploy
   ```

   Workers Builds installs the lockfile dependencies. The `&&` stops deployment if migration fails. The command runs on the build host, not in the Worker or a Wrangler custom build hook. Use the Wrangler configuration generated by the same build and verify its target before enabling deployment.

## Failure and recovery

A failed migration rolls back its transaction and history. Inspect the build log without exposing secrets, fix the cause, and retry only after confirming the target and release order. Do not manually edit migration history to bypass a failure.

If migration succeeds but deploy fails, the old Worker still uses the new schema. Every release must use backward-compatible expand/contract changes: add compatible schema first, deploy code, and remove old schema only in a later safe release after old versions and rollback no longer need it. Rolling back the Worker does **not** roll back the database. Investigate and retry the deploy; do not automatically reverse migrations or drop data.
